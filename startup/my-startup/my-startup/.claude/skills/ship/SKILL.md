# /ship — 기능 하나 출시하기

사용자가 `/ship`이라고 부를 때만 실행한다. 한 번에 기능 하나만 다룬다.
이 매뉴얼을 쓰는 내내 CLAUDE.md의 규칙을 지킨다. 특히 아래 세 가지는 어기지 않는다.
- 실제 `data/entries.csv`를 지우거나 덮어쓰지 않는다. `python make_sample.py --reset`은 쓰지 않는다.
- `git commit`, `git push`는 하지 않는다.
- PRD.md에 없는 기능은 만들지 않는다.

## 1단계. 기능 고르고 먼저 말하기
- `$ARGUMENTS`에 번호(예: F3)가 있으면 그 기능이다. 없으면 PRD.md 6장에서 체크(`[x]`)가 없는 기능 중 번호가 가장 작은 것을 고른다.
- 고른 기능의 이름과 PRD 4장의 완료 기준을 쉬운 말로 사용자에게 먼저 말한다.
- 번호를 안 줘서 내가 고른 경우에는 "이 기능으로 시작할까요?"에 사용자가 답할 때까지 기다린다. 번호를 줬으면 알린 뒤 바로 진행한다.
- 이미 체크된 기능이면 "이미 출시됨"이라고 알리고 멈춘다.

## 2단계. 만들기
- 시작 전에 `md5sum data/entries.csv`로 실제 기록 파일의 지문을 적어 둔다.
- 그 기능만 만든다. 계산은 logic.py, 파일 읽기/쓰기는 storage.py, 화면은 app.py에 둔다.
- PRD 완료 기준을 하나씩 확인하는 pytest를 같이 만든다. 테스트는 임시 파일만 쓴다.
- 새 기능이 예전 기능의 완료 기준과 부딪히면(예: 기분 태그가 필수가 되면 F1 저장 방식이 바뀜) 어느 기준이 어떻게 바뀌는지 사용자에게 말한다.
- 끝나면 `python -m pytest`를 돌려 전부 통과하는지 확인한다.

## 3단계. 직원 3명에게 차례로 검사받기
순서는 qa-tester → ux-reviewer → pm-checker다. 각 직원에게 "방금 만든 기능과 그 완료 기준을 검사해 달라"고 맡기고, 보고서(표)를 받는다.
- 직원 파일이 `.claude/agents/`에 있어도 이 대화에서 바로 안 불러지면, 읽기 전용 Explore 에이전트에게 그 직원 파일의 본문 지시를 따르게 해 대신 맡긴다. 이때는 사용자에게 대역으로 돌렸다고 알린다.
- ❌ 또는 ❔가 하나도 없어야 그 직원을 통과로 본다. 확인 못 한 건 통과가 아니다.

## 4단계. 문제가 나오면 고치고 다시 검사받기
- 직원이 ❌나 ❔를 보고하면 그 내용을 보고 직접 고친다. (직원은 고치지 않는다.)
- 고친 뒤 `python -m pytest`를 다시 돌리고, 문제를 말한 직원에게 다시 검사받는다.
- 고친 곳이 앞 순서 직원의 검사 대상에도 영향을 주면 그 직원도 다시 검사받는다.
- 한 직원에 대해 "고치기 → 재검사"는 최대 3번까지 한다. 3번 해도 통과하지 못하면 멈추고 사용자에게 묻는다. 물을 때는 지금까지 시도한 것, 남은 문제, 선택지(예: 기준을 바꿀지, 더 시도할지, 이 기능을 미룰지)를 쉬운 말로 적는다.

## 5단계. 다 통과하면
- 끝날 때 `md5sum data/entries.csv`를 다시 비교한다. 지문이 다르면 완료 표시를 하지 않고 사용자에게 알린다.
- PRD.md 6장에서 그 기능을 `[x]`로 바꾼다.
- GitHub에는 올리지 않는다. 커밋도 하지 않는다. 대신 커밋 메시지만 한 줄(필요하면 본문 2~3줄) 제안한다.

## 6단계. 최종 보고
직원별로 처음 결과 → 고친 것 → 최종 결과를 표로 보고한다. 아래 모양을 쓰고 마지막에 커밋 메시지 제안을 붙인다.

| 직원 | 처음 결과 | 고친 것 | 최종 결과 |
|---|---|---|---|
| qa-tester(테스트 담당) | | | |
| ux-reviewer(화면 검사) | | | |
| pm-checker(기획 검수) | | | |

고치지 않아도 됐으면 "고친 것"에는 "없음"이라고 쓴다.
